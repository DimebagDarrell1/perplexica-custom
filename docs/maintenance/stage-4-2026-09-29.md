# Stage 4: optional Jev reranking

Completed locally on September 29, 2026. Jev is implemented but remains disabled. Nothing was committed, pushed, deployed, or enabled against a paid provider. Existing data files match the pre-stage hashes.

## Finding

The most useful initial experiment is reranking discovered snippets before choosing pages to read. The existing workflow already supplies a bounded embedding shortlist, so Jev can make a narrow relevance decision without replacing discovery, extraction, or answer generation. This follows the approach in [TypeSafe's reranking cookbook](https://docs.typesafe.ai/cookbooks/rerank_typesafe).

This is a plausible benefit, not a measured improvement in this fork. No dedicated Jev key was configured, so no live inference or search-quality benchmark was run. The implementation should remain off until representative searches show a worthwhile improvement in selected sources, answer quality, latency, and cost.

## Added and changed

- Added a native HTTP adapter for TypeSafe and OpenRouter Decisions, with provider-specific pinned model defaults. No SDK or new dependency was installed. The adapter uses a dedicated `JEV_API_KEY` and never borrows credentials from saved chat providers.
- Added optional reranking between embedding ranking and URL selection in balanced and quality modes. Speed mode and chats with attachments skip Jev. Standalone follow-up queries are used when available.
- Send one bounded batch of named yes/no relevance questions. Defaults are 24 candidates and two seconds; hard limits are 32 candidates, five seconds, 128 KiB request bodies, and 64 KiB response bodies. Query, title, and snippet text also have token limits.
- Restrict candidates to discovered web, academic, and discussion snippets. Uploaded files, already-extracted pages, recognizable local URLs, and arbitrary metadata are excluded. URL fields are not sent. Provider calls use fixed HTTPS endpoints, reject redirects, and have no automatic retries.
- Validate returned answer types, IDs, and numeric ranges before applying the order. Ties retain the original order, unscored candidates stay in place, and source objects and citation metadata are preserved. Failure retains the original embedding ranking. Stop and context timeout cancel the request.
- Added `services.jev` to the research health response. It reports configuration, not tested availability, and does not call the provider. Added structured attempt logs containing status, bounded failure categories, counts, timing, model, and returned usage, without queries or snippets.
- Added disabled-by-default environment mappings to both Compose files. Existing images and remote builds were not replaced or launched.
- Added `yarn eval:jev`, six synthetic evaluation examples, and an explicit `--live` mode. Default evaluation is offline, even if credentials are present. Live mode requires explicit enablement and a dedicated key, makes at most six requests, and stops on the first provider failure. Example ordering is authored fixture order, not a measured embedding baseline.
- Added [setup, data-flow, limits, and evaluation documentation](../installation/JEV.md), linked from the existing PR-test research guide.

## Evaluation limits and remaining work

Contract tests use controlled responses; they establish integration behavior, not Jev's semantic accuracy. There has been no live test of either Jev provider. The six authored cases are a smoke test, not a representative benchmark. Provider latency, actual cost, multilingual quality, and source-selection benefit remain unmeasured.

The review used the [TypeSafe API schema](https://api.typesafe.ai/openapi.json), [model documentation](https://docs.typesafe.ai/models), [known limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13), and [OpenRouter's official integration guide](https://openrouter.ai/blog/tutorials/how-to-use-jev/). API contracts were checked on September 29, 2026.

Jev-based query generation, replacement of the answer model, research stop/go decisions, and citation verification were not added. Those would either require text generation or additional evaluation and calls beyond this optional reranking step.

Stage 5 remains final Docker/CI and live-service verification. It has not started.
