# Stage 3: cancellation and retrieval reliability

Completed locally on September 29, 2026. Stages 1 and 2 and unrelated working-tree changes were preserved. Nothing was committed, pushed, or deployed.

## Changes

- Added an accessible Stop response button to the follow-up input, including its multiline layout and a disabled Stopping state. A stop requested before the session ID arrives is queued. Cancelled answers display a saved-partial-answer notice.
- Added `POST /api/chat/[id]/stop`. Cancellation reaches classification, research, answer generation, embeddings, SearXNG, scraping, weather requests, and stock requests. OpenAI-compatible providers receive SDK request signals; Ollama uses a request-specific client so stopping one response does not abort another chat.
- Save partial answer blocks with a `cancelled` status before sending the terminal event. Normal completion also persists before notifying the browser. Existing SQLite text storage accepts the additional status without a data migration. Cancellation skips automatic follow-up suggestions and media searches.
- Preserve research across browser disconnection. Initial and reconnect streams share one transport and expose the actual backend session ID. Replay stores immutable event snapshots, cleans up completed subscriptions, and handles errors without an attached browser. Missing reconnect sessions only mark still-answering messages as failed.
- Replaced the duplicated stream parsers with a JSON-lines reader that handles split UTF-8 and partial lines without replaying earlier events. Chat HTTP failures now produce an error state. Interrupted connections prompt the user to reload and reconnect.
- Keep web snippets when deep page extraction fails, including searches with attached files. Fallback reserves space for both file and web evidence. Unread sources can contribute snippets alongside successfully extracted pages. Scrape failures no longer become fake citation sources.
- Include retrieved file excerpts once. Initial excerpts are only added for files absent from the selected evidence, with a shared 3,000-token allowance. The user-message attachment list contains names instead of another copy of the excerpts.
- Bound selected evidence text to 8,000 tokens in speed mode, 16,000 in balanced mode, and 32,000 in quality mode, measured with the existing tokenizer. These are evidence budgets, not total model context limits. Instructions, history, widgets, and fallback file excerpts are additional.
- Speed mode deep-reads up to three URLs instead of five and limits context processing to 15 seconds instead of 45. Balanced and quality retain their existing URL and time limits. Context timeout cancels its own embedding and scrape requests while allowing the writer to use fallback evidence.
- Removed prompt instructions that force three queries or five to six search iterations when fewer would answer the question. A `done` tool no longer discards other calls in the same batch. Explicit URL extraction is capped at 50,000 characters and eight extraction chunks per page.
- Accepted whitespace-only tool arguments without a parser crash and keyed streamed tool calls by their supplied index, including sparse indexes.
- Prevented Enter during IME composition from submitting either message input. Follow-up form submission always prevents native navigation, including while busy. File-upload failures show an error and clear the loading state; the same file can be selected again. Clear attachments no longer submits the form.
- Fixed a settings-file race observed during the production build. Settings now use a temporary file and atomic rename. An unreadable settings file is preserved and reported instead of being overwritten with defaults.

## Limits and next stages

Already-running local transformer computations cannot be forcibly interrupted; cancellation stops waiting and prevents later work. Provider initialization occurs before the streamed session becomes available. Sessions remain in memory and do not survive a server restart. Real providers, self-hosted Firecrawl, Linux Docker, and Unraid deployment have not been exercised in this stage.

Stage 4 is the Jev evaluation and any justified optional integration. Stage 5 covers final Docker/CI and live service verification. Both remain pending the user's instruction to continue.
